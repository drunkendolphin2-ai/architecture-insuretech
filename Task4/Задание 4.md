# Решение
1) Веб отправляет запрос с заявкой
2) core генерирует requestId, открывает sse, сохраняет в redis связку requestId - instanceId
3) core отправляет событие в топик заявок
4) Агрегатор читает топик заявок, сохраняет в базу данных 
5) Агрегатор с помощью крон джобы отправляет запросы страховым компаниям, сохранят заявку в статусе PROCESSING 
6) Агрегатор с помощью крон джобы запрашивает информацию по решению у страховых компаний по заявкам в статусе PROCESSING, сохраняет ответ, отправляет в топик решений по заявке 
7) core читает очередную запись, сохраняет данные в редисе и Б, проверяет по requestId, какой instanceId привязан к заявке
8) если это его requestId - отправляет данные по SSE клиенту.
9) иначе отправляет нотификацию через Pub/sub другому инстансу, который уже отправляет данные по SSE.
10) В случае разрыва соединения - отправляется новый запрос с тем же requestId, и запись redis обновляется

# Дополнительно
1) Поскольку партнеров мы ожидаем максимум 60 секунд нужно установить таймаут.
2) Ретраи в агрегаторе нужны только при запросе решений по заявке, в противном случае может быть ситуация, когда партнер принял заявку, начал ее обработку, ответил ошибкой, и агрегатор снова отправляет запрос на создание заявки
3) Решение никак не ломается от нескольких экземпляров, джобы можно ограничить либо через shedlock, либо блочить строку в БД, чтобы в момент времени только 1 джоба обрабатывала заявку
4) curcuit breaker нужен на связи со страховыми компаниями, поскольку если сервер компании лежит, то нет смысла ходить туда лишний раз
5) рейт лимит нужен на исходящие в страховые компании запросы, иначе в пике будет огромное количество запросов, что вряд ли понравится партнерам
6) для страховых компаний с истекшим сроком обработки заявки - в агрегаторе отправляет событие в топик решений, что решения нет, а дальше флоу как обычно
